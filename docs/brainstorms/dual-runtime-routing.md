## Problem Statement

Developers using NeonCore should get a seamless experience that combines **Gridlight**
(local AI, hardware- and model-dependent) with **Claude / Codex** (hosted), using each
where it excels and maximizing tokens. Gridlight is likely best for bash and quick
answers; if the local box can run a capable code model, NeonCore could route full
code-change queries to the Gridlight terminal instead of a hosted model. The end state:
a cartridge can have both runtimes connected, and NeonCore picks the best one per query.

## Scoped Definition (what Phase 1 commits to)

Phase 1 scopes only the **wedge**: a reusable, per-model **behavioral parity eval** for
the Gridlight terminal. Everything else (hardware probe, auto-routing, per-step terminal
selection in workflows) is explicitly deferred to later phases and depends on this.

Decisions locked during interrogation:
- **Wedge:** Parity validation harness (Task 0). Validate before building routing.
- **Parity bar:** **Behavioral** — same outcome, method may differ. Not mechanistic
  ("same tool surface"), not protocol ("same events"). We prove Gridlight lands the
  same result, and let Gridlight be Gridlight.
- **Harness scope:** **Reusable per-model eval** whose accuracy score NeonCore later
  consumes for routing — so Task 0 and Task 1 compound rather than being separate builds.

## Status Quo (what's true in the code today)

Grounded in `neoncore/` and `../vscode-extension/` (the Gridlight monorepo), not
speculation:

- **Runtime is already modeled.** `AgentType = 'claude' | 'gridlight' | ...` and
  `TranscriptEngine = 'claude' | 'gridlight'` (server/src/types.ts). Cartridges map to
  agents; workflow steps dispatch on `executorId`.
- **The Gridlight terminal already exists** in `../vscode-extension` as a monorepo:
  portable `@gridlight/core` engine + `gridlight-vscode` extension + `@gridlight/cli`
  (Ink TUI). Tool surface is nearly 1:1 with Claude Code: `read_file`, `write_file`,
  `edit_file`, `search_code`, `list_files`, `run_command` (persistent bash), git,
  web fetch/search, `spawn_agent`, diagnostics, MCP
  (`packages/core/src/agent/agentTools.ts`).
- **NeonCore integration is already first-class** (`packages/vscode/src/neoncore/`):
  registers as `agentType: 'gridlight'`, reports activity (`PostToolUse`,
  `UserPromptSubmit`, subagent events) via `activityReporter.ts`, streams transcript +
  token usage with `engine: 'gridlight'` into the same `messages` table as the Claude
  reporter, honors the remote permission proxy (long-poll `/api/permissions`), and
  accepts remote command injection (`command_send`).
- **Gaps:** (1) **no hardware detection** anywhere (no RAM/VRAM/GPU probing);
  (2) "local" means pointing Gridlight at an external Ollama / LM Studio / vLLM over
  HTTP (default model `llama3.1`, weak at code) — there is no embedded local runtime.

## Premises (challenged during interrogation)

1. **Transport + tools + protocol already exist — Task 0 tests the *model*, not
   integration.** Sending a query to the Gridlight terminal is the existing dispatch
   path; the tool surface and NeonCore reporting are built. So the wedge is an
   output-quality eval, not a build. **Agreed (code-verified).**
2. ~~Behavioral parity ≠ interchangeability in workflows (no gridlight-reporter).~~
   **Retracted.** Gridlight already reports activity/transcript/tokens/permissions to
   NeonCore natively (it doesn't need a shell reporter hook). Workflow interchangeability
   (Task 3) is mostly already there.
3. **Hardware predicts speed; the *model* predicts accuracy.** A fast GPU running a weak
   model is fast and wrong. Accuracy is only knowable by evaluating outputs — which is
   what the harness does. Confirmed and sharpened: Gridlight has no hardware detection and
   the served model is a free variable, so the accuracy signal must be **per-model**.
   **Agreed.**
4. **Auto-routing needs a query classifier with a verify/fallback loop.** Judging a
   query's difficulty before running it has real error cost (misroute a hard refactor to
   a weak local model → bad code, wasted time). The manual toggle avoids this; auto-routing
   needs a classifier + fallback. **Agreed — deferred past the wedge.**

**Core insight:** the hard problem was never integration (done). It's **trust** — knowing
whether the model this Gridlight is pointed at, on this box, is good enough for a given
query class. The per-model eval is the keystone; hardware probe and routing are decision
logic layered on a trustworthy score.

## Approaches Considered

### Approach A: Deterministic task-suite (minimal viable) — RECOMMENDED
Fixed suite of coding tasks (bash, read, edit, multi-file refactor, search, git) run
through `@gridlight/cli` pointed at a local model, scored by **hard outcome assertions**
(file end-state, exit code, expected output) against a Claude reference. Per-capability +
aggregate score stored as JSON keyed by model id. Reuses gridlight core/CLI — no new
agent code.
- **Effort:** S/M (CC: ~1-2 sessions). **Risk:** Low.
- **Pros:** fast; deterministic = trustworthy; re-runnable per model; score feeds routing
  directly; reuses existing execution.
- **Cons:** authoring good assertable tasks takes effort; deterministic checks miss
  subjective code quality.
- **Reuses:** `@gridlight/cli`, `@gridlight/core` tool loop, existing NeonCore transcript
  pipeline.

### Approach B: Eval + LLM-judge + NeonCore readiness panel (ideal architecture)
Suite from A plus an LLM-judge rubric for subjective quality (behavior preserved,
idiomatic) and a capability matrix that also asserts protocol events fire. Results stored
in the NeonCore DB (per model, timestamped) and surfaced as a "Gridlight readiness"
dashboard panel.
- **Effort:** M/L (CC: ~3-4 sessions). **Risk:** Med (judge variance, more surface).
- **Pros:** richest signal (accuracy + quality + protocol); visible in product; wired to
  routing.
- **Cons:** bigger; judge cost/variance; more to maintain.
- **Reuses:** everything in A + NeonCore DB + dashboard.

### Approach C: Shadow-run on real queries (creative/lateral)
No synthetic suite. On a dual cartridge, Claude runs the query for real while Gridlight
runs the same prompt in an isolated worktree; NeonCore diffs outcomes and logs an
agreement/quality score per query class over real usage. The eval builds itself from
actual work.
- **Effort:** M (CC: ~2-3 sessions). **Risk:** Med/High.
- **Pros:** no synthetic task authoring; real-world-representative; naturally per-model and
  per-query-class; compounds with usage.
- **Cons:** doubles token/compute on shadowed queries; sandbox isolation is fiddly; noisy
  scoring; slow to accumulate confidence.
- **Reuses:** dual-cartridge UI (Task 2), NeonCore diff/transcript.

## Recommended Approach

**Approach A**, because it is the fastest path to a trustworthy, re-runnable accuracy
signal that Task 1 routing can consume, and it reuses `@gridlight/cli` + core with no new
agent code. Start deterministic; graft B's LLM-judge and C's shadow-mode on later, once
the harness exists and you know which task classes actually matter. This is the smallest
self-contained unit that de-risks the entire effort — matching the stated goal of
splitting a big task and taking it one at a time.

## Phased Roadmap (the "big task, split up")

- **Phase 1 (this doc):** Interrogate + scope the wedge. ← you are here
- **Task 0 / next build:** Reusable per-model behavioral parity eval (Approach A).
- **Task 1:** Hardware probe (new — none exists) + routing that reads the per-model score.
  Split: (a) hardware/model probe advisory badge; (b) routing decision using score +
  probe.
- **Task 2:** Dual-run cartridge — both runtimes connected, shown in UI, manual pick per
  query (mostly UI + dispatch; protocol plumbing already exists).
- **Task 3:** Re-add per-step terminal dropdown in workflows (the one just removed at the
  cartridge level), offering whichever terminals are connected. Depends on Task 2.

## Open Questions

1. Which local models are in scope for the first eval run (e.g. `llama3.1` baseline vs
   `qwen2.5-coder-*`)? The default `llama3.1` will likely score poorly on code.
2. Where should the eval live — a new package in `neoncore/`, or inside the Gridlight
   monorepo next to `@gridlight/cli`? (Leaning NeonCore, since it consumes the score.)
3. Is a Claude reference run required each time, or do we assert against static golden
   outcomes (cheaper, no hosted cost per eval run)?
4. What query classes matter most for routing — is "bash / quick answer vs full code-gen"
   the right first taxonomy, or finer (edit vs multi-file refactor)?
5. Score → routing threshold: who sets it, and is it per-class?

## Success Criteria

- `eval run --model <id>` produces a per-capability + aggregate behavioral-parity score
  for a Gridlight-served local model, stored and re-runnable.
- The stored score is in a shape Task 1 routing can read directly (per model, per class).
- Zero new agent/tool code in Gridlight — the harness only drives existing capabilities.

## Effort Estimate

the task suite and outcome assertions, not by new infrastructure.

### Model backend (`packages/core/src/api/gridlightClient.ts`)

- `gridlight.backendMode = 'gridlight' | 'openai-compatible'` (host/config.ts:8).
- **Gateway (default):** remote HTTP `POST /chat/intelligent` to `gatewayUrl`
  (default `http://localhost:8080`), model `gridlight-default` (server-side auto-select).
- **OpenAI-compatible (local):** `chatOpenAI()` → `${gatewayUrl}/v1/chat/completions`,
  streaming; documented for **Ollama / LM Studio / vLLM**; default model `llama3.1`.
- Built-in registry: claude-3-5-sonnet / opus / haiku, gpt-4-turbo, gpt-3.5 + user
  `customModels` (vscode/src/models/modelRegistry.ts:53).
- **Hardware detection: NONE.** No RAM/VRAM/GPU probing anywhere in `packages/`.
