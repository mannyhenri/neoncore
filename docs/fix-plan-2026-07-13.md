# Bug Fix Plan — 2026-07-13

Compiled from a 5-step NeonCore workflow (Static Analysis → Dead Code Scan → Bug Pattern
Hunt → Plan). All findings verified against the code at the line numbers cited.

> **Why this file exists:** completed workflow runs are hard-deleted 30 seconds after they
> finish (P1-1 below). Without persisting it, the output of the run that produced this plan
> would be destroyed. See P1-1.

## P0 — Critical (2)

| File:Line | Issue | Fix |
|-----------|-------|-----|
| `server/src/lib/workflow-executor-v2.ts:1527` (`tick`) | `tick()` runs on `setInterval` and calls `processWorkflow(id)` (line 1534) in a bare loop. No try/catch anywhere in the chain; `normalizeStep()` does an unguarded `JSON.parse(row.executor_config)`. There is **no** global `uncaughtException` handler in `server/src`. A sync throw inside a `setInterval` callback is an uncaught exception → **the whole server process dies**, and on restart tick hits the same row again → crash loop. A throw for workflow A also starves workflows B..N in the same tick. | Wrap the loop body: `for (const { id } of runningWorkflows) { try { processWorkflow(id); } catch (err) { console.error(...); } }` so one poisoned workflow cannot kill the tick or the process. Separately guard the `JSON.parse` in `normalizeStep` (fall back to `{}` and log). Add `process.on('uncaughtException')` / `('unhandledRejection')` handlers in `index.ts` as a backstop. |
| `server/src/lib/workflow-executor-v2.ts:1321` (`processWorkflow`), plus `:1203` and `:1264` (`processDeliberationStep`) | **`idle` does not mean "finished."** `index.ts:115` sets `IDLE_THRESHOLD_MS = 2min`; the sweeper at `index.ts:152-167` flips an agent to `idle` after 2 min of no *hook* activity. Hooks fire only *after a tool returns*, so an agent in one long operation (test suite, build, big grep, or parked on a permission prompt) is marked idle **while actively working**. The executor then completes the step and harvests the last `assistant_message` (mid-work chatter) as the step **result** — review/quality gates then parse PASS/FAIL from that garbage. The `MIN_RUNNING_BEFORE_COMPLETE_MS = 60_000` guard (line 20) is a **no-op**: idle cannot occur before 120s, so a 60s floor never binds. | Stop treating idle as a completion signal. The correct signal already exists and is proven: the webhook / `neoncore_report_step_done` path (`routes/workflows.ts:975`), which standard steps already use. Preferred: delete idle-based completion and require gates to report explicitly. Minimum viable: raise the floor above `IDLE_THRESHOLD_MS` **and** require a real terminal marker (e.g. an explicit PASS/FAIL token) before completing — never complete on silence alone. **Must patch all three sites (1203, 1264, 1321)**; fixing only one leaves the race live. |

## P1 — High (3)

| File:Line | Issue | Fix |
|-----------|-------|-----|
| `server/src/lib/workflow-executor-v2.ts:1508-1515` | **Data loss.** On completion, runs are hard-deleted after 30s: `setTimeout(() => { DELETE FROM workflow_steps ...; DELETE FROM workflows ... }, 30_000)`. Every step result — the entire output of a review/analysis workflow — is destroyed half a minute after it finishes. The user can never read a completed run. This is also why mobile has nothing to drill into: **the run is gone**, not merely unrendered. The timer is uncancellable; a late webhook after deletion silently updates 0 rows. | Product decision, not a mechanical fix. Options: (a) stop deleting runs and add explicit retention/cleanup (`cleanup-scheduler.ts` already exists — use it); (b) persist results to `docs/` or a `workflow_results` table before deleting. | `server/src/lib/send-command.ts:40, :52` | **Silent failure on the dispatch path.** Both AppleScript delivery attempts swallow their exception (`catch { /* fall through */ }`, `catch { /* ignore */ }`) and fall through to `return false`. Delivery failure produces zero diagnostics and the step stays `running` forever. This is the silent-hang class already documented in `STATE.md`. | Log the caught error at minimum. Then propagate: when `sendCommandToAgent` cannot deliver, mark the step **failed** with "no command channel" rather than leaving it `running`. |
| `server/src/index.ts:283` + `server/src/routes/workflows.ts:975` | **No auth, bound to all interfaces.** `server.listen(PORT, '0.0.0.0')` with **no** auth middleware anywhere (no API key, bearer, or origin check — verified). Any device on the LAN can POST `/api/workflows/webhook/:stepId/complete` to forge step results, or hit send-command to inject an **arbitrary prompt into a live Claude Code agent** — RCE by proxy. The webhook's `result` body is unvalidated (no type/size check) and goes straight into SQLite. | Add a shared-secret/API-key middleware (env var, sent by relay + hooks + mobile), or bind to `127.0.0.1` and require a tunnel for remote use. Validate `result` is a string and cap its length. Severity depends on network trust — raise before this box sits on an untrusted network. |

## Cross-cutting: the real root cause

Four separate findings are the same disease — **the system reports success it has not verified**:
silent dispatch failure (P1-2), completion inferred from silence (P0-2), results deleted before
anyone reads them (P1-1), and a relay whose deps were never installed (the original bug in
`STATE.md`). The durable fix is not any single patch: it is that **a step should only complete on
an explicit, positive signal from the agent** — which the `report_step_done` webhook already
provides and which this very workflow proved works end-to-end.

## Guardrails for the implementation step

- **Safe to auto-implement:** P0-1 (try/catch + global handlers), P2 heartbeat logging, P3 unused
  imports/locals, `ruff --fix`, the 4 dead exports.
- **Needs a human decision — do NOT auto-implement:** P1-1 (run deletion — data-retention policy),
  P1-3 (auth model), P3 epic autopilot (~2,600 lines; ship or delete), and the *shape* of the
  P0-2 fix (removing idle-completion changes gate semantics).
- Nothing here has test coverage. There is **no lint config in the repo at all** — no ESLint/Biome
  anywhere — so nothing but `tsc` will catch a regression. Verify by running the server and
  driving a real workflow through the relay.
