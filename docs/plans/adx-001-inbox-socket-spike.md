# ADX-001 — Can we reach a busy cartridge over its inbox socket?

*Measured 2026-09-08 on macOS 15 (Darwin 25.5.0), Claude Code **2.1.266**
(the epic's floor is 2.1.224). Held to the code by
`server/test/adx-001-spike.test.ts`, so a finding that drifts fails rather than
misleads.*

## The answer, in one line

**Yes — and the token turned out not to be the gate.** On macOS a message posts
to `/tmp/cc-socks/<pid>.sock` and is delivered **with no auth line at all**. The
epic's one shape-changing risk is not present on this platform.

## What was asked, and what was found

| Question | Answer |
|---|---|
| Can the relay READ `CLAUDE_CODE_MESSAGING_TOKEN` from its PTY child? | **No.** |
| Can the relay know the token anyway? | **Yes — by INJECTING it before spawn.** |
| Does a post succeed WITHOUT the auth line on macOS? | **Yes — delivered.** |
| Does a post succeed WITH the auth line? | **Yes — delivered.** |
| Does a WRONG token block delivery? | **No — delivered anyway.** |

## The evidence

### The token cannot be read out of the child

`ps eww -p <pid>` does expose a same-uid process's environment on macOS, so the
obvious approach looks viable — and it is not, because what `ps` shows is the
**exec-time** environment. `CLAUDE_CODE_MESSAGING_TOKEN` is generated by the
`claude` process *after* exec and lives only in its own memory.

Measured against a real relay-owned session (pid 46585, whose parent 46582 is
`agent/relay/index.js` — i.e. exactly the configuration this epic targets):

```
ps eww -p 46585 | grep -o "CLAUDE_CODE_[A-Z_]*" | sort -u
  → CLAUDE_CODE_MAX_OUTPUT_TOKENS          # inherited at launch
                                           # MESSAGING_TOKEN absent
env var count visible via ps : 47
env var count a CHILD of claude sees : 60  # claude ADDS the token for children it spawns
```

The direction matters and is the trap: a process spawned **by** claude receives
the token; the relay is claude's **parent** and does not.

### But the relay can inject one

The relay already controls the environment it spawns with —
`agent/relay/index.js:235` passes `env: process.env` into `pty.spawn`. Setting
`CLAUDE_CODE_MESSAGING_TOKEN` there means the relay knows the token *by
construction* rather than by discovery.

Proven: a session spawned with an injected token showed that exact token in
`ps eww` output (`injected_token_visible_in_ps: true`), because an injected
value **is** part of the exec-time environment.

This is a materially different capability from reading one, and ADX-002 should
be written for injection, not for extraction.

### Delivery works, with or without auth

Wire format, read out of the CLI bundle rather than guessed — it ships a worked
example:

```
{ echo '{"type":"auth","token":"'"$CLAUDE_CODE_MESSAGING_TOKEN"'"}';
  echo '{"type":"user","message":{"role":"user","content":"hello"}}'; } | socat - UNIX-CONNECT:<sock>
```

Three probes against a live throwaway session, each carrying a unique marker,
delivery confirmed by watching the child's own PTY output rather than by the
socket's silence:

| Probe | Socket error | Delivered |
|---|---|---|
| no auth line | none | **yes** |
| wrong token | none | **yes** |
| correct token | none | **yes** |

**Control** — a session spawned with *no* `CLAUDE_CODE_MESSAGING_TOKEN` in its
environment at all, posted to with no auth line: **delivered**. So the
permissive result is not an artefact of the injection.

On macOS the socket is `srw-------` (mode `0600`) and owned by the user, so the
filesystem *is* the authentication. This matches the epic's own note that
Windows named pipes are the platform that requires the auth line.

### Two facts the probe established for free

- **The socket is removed when the process exits** (`socket_removed_on_exit:
  true`), so a stale path means a dead session — useful for ADX-003's failure
  typing.
- **10 sockets are live, not the 9 the epic recorded**, and one of them
  (`94544`) is a `claude bg-spare` under a `bg-pty-host` daemon rather than a
  relay-owned session. That is ADX-009's registry delta, visible already.

## What this means for the epic

**The shape does not change. Two tasks get easier and one caveat is added.**

- **ADX-002 (relay reports PID + token)** — still worth doing and now trivial:
  the relay *generates* the token and passes it in at spawn, then reports it.
  It must not be written as "read the token from the child", which is the thing
  proven impossible above. On macOS the token is not required for delivery, so
  this task is about Windows parity and about not depending on a permission
  model that may tighten.
- **ADX-003 (socket client)** — the auth line becomes **optional on macOS and
  mandatory on Windows**, which the epic already anticipated. The JSON shapes
  above are the contract. Note the CLI's own client additionally verifies the
  endpoint's pid and uid before writing; our client should do the same rather
  than trusting the path, since a stale socket path can be re-bound by a
  recycled pid.
- **Nothing is blocked.** ADX-001's fourth acceptance criterion — "if the token
  cannot be obtained, state the epic's revised shape" — is satisfied by the
  finding that delivery does not need it.

## The one caveat worth carrying

A brand-new session parked on the **trust-this-folder** prompt accepts socket
connections and delivers nothing, with no error on either side. The first run of
this spike reported a clean negative for exactly that reason, and it looked
identical to a broken transport. ADX-003 should treat "connected, wrote, no
observable effect" as its own failure mode rather than as success, and ADX-005
should not read a silent socket as proof of delivery.
