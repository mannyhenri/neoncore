## Prior Work Summary

### CLAUDE.md Relevant Notes

- **Skill routing is the front door.** CLAUDE.md maps intent → skill (`/investigate`,
  `/qa`, `/ship`, `/context-save`…). A scheduled job is a *dispatch of one of these*, not a
  new execution concept. Anything built here should schedule the existing vocabulary rather
  than invent a parallel one.
- **The Work Standard is enforced, not advisory**, and it is explicitly *not* armed by
  investigation: `armOnWork` binds only when an agent first edits a file. **This matters
  enormously for a morning report.** A read-only "status of repo X" job touches nothing, so
  it never arms the contract and the Stop hook will not demand a completion report. Reporting
  jobs are already the shape the standard tolerates.
- **Caveat carried from the same doc:** the Stop hook refuses to let an agent finish without a
  completion report once armed, capped at 2 blocks, after which the cartridge is flagged
  `needs_review`. An unattended job that *does* edit something and then stalls will sit
  flagged with nobody watching. Any automation design must say what happens to a 3am
  `needs_review`.
- **New workflows get a Work Standard gate appended automatically** — so does a Workflow
  Completion Report step (added 2026-09-17). A scheduled run therefore already produces a
  self-contained HTML + JSON report and opens it. **Half of "and provide a report" is built.**

### Verdict

**PRIOR WORK EXISTS — and more of this is already built than any document says.**

Key context for Phase 2:

1. **The scheduler is built, wired and running.** `lib/heartbeat-scheduler.ts` polls every 60s
   (`startHeartbeatScheduler()` at `server/src/index.ts:312`). The `heartbeats` table supports
   `hourly` / `daily` / `weekly`, and its schema default is literally
   `{"type":"daily","time":"09:00"}` — "every morning" is the built-in default. Full CRUD at
   `routes/heartbeats.ts` including `POST /:id/fire`, plus a dashboard UI in `GoalsPage.tsx`.
   A USD budget gate skips a fire when the project's goal is over budget, and emits a
   `heartbeat_fired` notice saying so.

2. **It has never been used: 0 heartbeats in the live database.** The plans assumed this was
   missing; it is not. It is unexercised, which is a different problem and a much smaller one.

3. **THE BLOCKER, reproduced — a fired heartbeat produces a run that cannot execute.**
   `heartbeats` has an `agent_id` column, `routes/heartbeats.ts` reads and writes it, and the
   dashboard collects it. **Neither `fireHeartbeat` nor `checkDueHeartbeats` ever passes it on,
   and `cloneTemplateAsRun(templateId, projectId, extraContext)` has no parameter for it** — it
   copies `executor_id` verbatim from the template, where every agent step is `'__deferred__'`.
   Reproduced against a seeded template: **7 of 8 steps land with no cartridge while the run is
   marked `running`.** The manual launch path guards this exact case at the door
   (`unrunnableSteps()`, "validate while a human is watching"); the scheduled path does not
   check, and there is no human watching at 09:00. This is the one thing standing between
   today's code and a working morning report.

4. **Delivery is largely solved.** `lib/channels.ts` is an adapter registry with `notifyAll`
   fanout that deliberately knows nothing about any specific app; APNs push exists; and every
   workflow now ends in a Workflow Completion Report step that renders HTML + JSON. The open
   question is not *how to produce a report* but *how an unattended report reaches you* — the
   report step currently opens a local file, which nobody sees at 3am.

5. **"Research the latest news on Gridlight"** is the weakest leg. A `Deep Research` standard
   template exists, but no web-fetch/search capability appears in the server or the routing
   table — that research runs inside a cartridge using whatever tools its engine has. Phase 2
   must establish whether a scheduled Codex/Claude cartridge can actually reach the web
   unattended, or whether this leg needs a connector.

**The reframe Phase 2 should start from:** this is not "add automation to NeonCore". The
scheduler, the autonomy ladder, the budget gate, the notice fanout and the report renderer all
exist. It is **"make the existing heartbeat path survive an unattended fire, and give its
output somewhere to land."** That is a materially smaller and differently-shaped problem than
the Hermes and Discord plans were written to solve — both of which predate the autonomy work
shipping, and one of which supersedes the other.
